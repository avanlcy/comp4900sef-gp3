# Dead Fire Phase 4 (AI Racers) and Generator Readability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every graph-authoring step is automation through the generator pipeline; the only **(person)** step is the playtest in Task 7. The project manager chose native execution without a question round (as in Phase 3): the agent implements every task in this session and one fresh reviewer reads the result at the end.

**Goal:** Three NPC Sedans that race the loop on their own lanes, avoid cars, use items against the player, respawn after wrecks without ending the race and show up in the ranking, plus a Blueprint generator whose output has no author watermark and reads left to right in sections a person can follow.

**Architecture:** Every Blueprint is described in Python under `tools/bpgen/graphs/`, generated into `comp4900sef/Script/paste/<Asset>/` by `tools/bpgen/generate_all.py`, and applied inside the running editor by `comp4900sef/Script/df_apply_blueprint.py` through the DF Blueprint Authoring plugin. Phase 4 adds one gameplay module (`ai.py`: the AI controller), one test module (`tests_ai.py`), a test GameMode child, and extends the vehicle (AI inputs, aim target), racer (per-racer respawn timer, rank, item selection), GameMode (NPC spawning, registration, per-racer ticking, ranking, item supply, AI respawn), track (wrap, direction), HUD (position line) and the level builder (test GameMode). The readability work changes the generator library (`bpgen.py`: layout engine, sections, notes, docs), the runner and the plugin (node positions, function descriptions, graph focus), then touches every module once.

**Tech Stack:** UE 4.27.2 at `D:\UE_4.27`, Blueprint-only project `comp4900sef/comp4900sef.uproject`, PhysXVehicles, AIModule (`/Script/AIModule.AIController`), UMG, Functional Testing framework, editor Python 3.7 reached with `python tools/ue_remote.py --code "..."`, headless tests with `tools/run_tests.ps1`, VS 2019/2022 Build Tools for the plugin rebuild.

**Spec:** `docs/superpowers/specs/2026-10-30-phase4-ai-design.md` (driver §2, items §3, GameMode §4, HUD §5, values §6, readability §7, tests §8, acceptance §10). Base designs: `docs/superpowers/specs/2026-10-20-dead-fire-design.md`, `2026-10-21-phase2-race-flow-design.md`, `2026-10-30-phase3-items-design.md`.

### Task 1a: Layout engine, sections, notes, docs in `bpgen.py`; runner support

**Files:**
- Modify: `tools/bpgen/bpgen.py`, `comp4900sef/Script/df_apply_blueprint.py`, `tools/bpgen/graphs/items.py` (BP_DFBomb only, as the proving ground)

**Interfaces:**
- Produces (`bpgen.Graph`): `section(title: str)` — the next root node created (event, custom event, input action, component-bound event, or the first exec node linked from `entry`) starts a titled section; `note(node: Node, text: str)` — a comment bubble (`NodeComment`, `bCommentBubbleVisible=True`) on the node; `comment(...)` is removed (its one caller, `tests.T`, moves to `section`). `Graph.layout()` runs inside `text()` and assigns every node's `x`, `y`; `Graph.layout_info -> {"entry": [x, y] | None, "result": [x, y] | None}` for function graphs; `Graph.overlaps() -> list[str]` (pairs of node names whose rectangles intersect, 8 px margin) and `Blueprint.write` prints a `WARNING <asset> <graph>: overlap ...` line per entry (never raises).
- Produces (`bpgen.Blueprint`): `function(..., doc: str = "")` stores `doc` in the manifest function entry and titles the graph's section with it; `Blueprint(asset, parent, description: str = "")` → manifest `"description"`. Manifest graphs gain `"layout": {"entry": [x, y] | null, "result": [x, y] | null}`.
- Produces (runner): pass 1 calls `set_function_description` for functions with a `doc` (when the plugin has it); pass 2 applies `layout` with `set_node_position` for `entry`/`result` (skipping a missing result node) and sets `blueprint_description` from `description` before the compile.
- Layout contract (spec §7.3): exec nodes = nodes with an exec pin; roots = exec nodes with no linked exec input; column = longest exec path from a root (column 0 reserved for the function entry node in function graphs; event-graph roots start at column 0); rows by depth-first walk where the first exec output (`then`, `LoopBody`, cast success, `then_0`) keeps the row and each further output starts a new row below everything placed so far; pure nodes attach to the first exec consumer in (column, row) order (or to a virtual result sink at the last column + 1 for pure nodes linked to `result`), with depth = longest pure path to that consumer, placed in depth columns left of the consumer starting 40 px below its top and stacked 24 px apart; column x = previous column's right edge + 80 + the widest pure tree in this column; row y = previous row's bottom + 60; node sizes estimated from class and visible pin counts (`height = header (32, or 48 for events/casts/macros) + 24 × max(inputs, outputs) + 12`, width by class, call nodes `60 + 7.5 × len(function name)` clamped to 180–420); section boxes = bounding box of their nodes with 24 px padding and a 36 px title bar, colour `(0.35, 0.45, 0.6, 1)`, the function box including the entry and result rectangles; pure nodes that nothing consumes go in a trailing column.
